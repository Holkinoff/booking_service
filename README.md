# Сервис записи на приём с уведомлениями

Два микро-сервиса для записи клиентов к мастерам на временные слоты и отправки асинхронных уведомлений о бронировании, отмене и напоминаниях.

## Архитектура системы

1. **booking-service (FastAPI + Uvicorn)**:
   - Предоставляет REST API для управления бронированиями и просмотра свободных слотов.
   - Гарантирует целостность данных через транзакции PostgreSQL и сохраняет события в таблицу outbox_events (паттерн Transactional Outbox).
   - В фоновом цикле опрашивает outbox и публикует события в RabbitMQ, а также отслеживает записи для отправки напоминаний за 24 часа.
2. **notification-worker**:
   - Асинхронный консьюмер на aio-pika, обрабатывающий события booking.created, booking.cancelled и booking.reminder.
   - Проверяет дедупликацию событий через Redis (SETNX, 7 дней TTL).
   - Применяет Rate Limit: не более 3 уведомлений в час на одного клиента через атомарный счётчик Redis (INCR + EXPIRE).
   - Отправляет уведомления в клиентский канал с ретраями и перенаправлением в Dead Letter Queue (DLQ) при исчерпании попыток.


## Запуск проекта

Все зависимости и сервисы запускаются одной командой:

```bash
docker compose up --build
```

Сервисы и порты:
- **API сервис**: `http://localhost:8000` (Swagger UI: `http://localhost:8000/docs`)
- **Health-чеки**: `http://localhost:8000/healthz` (liveness), `http://localhost:8000/readyz` (readiness с проверкой БД, Redis, RabbitMQ)
- **RabbitMQ Management**: `http://localhost:15672` (логин/пароль: `guest`/`guest`)
- **PostgreSQL**: порт `5433`
- **Redis**: порт `6379`

При старте контейнера `booking-service` автоматически применяются миграции Alembic и запускается сидирование тестовых мастеров и их расписания.

## Тестирование

Тесты запускаются в изолированном Docker-окружении:

```bash
docker compose -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from test-runner
```

Покрытие тестами:
- **Юнит-тесты**: расчёт слотов, ограничение на запись минимум за 60 минут, проверка лимитов и идемпотентности.
- **Интеграционный тест на состояние гонки (Race Condition)**: 20 одновременных параллельных запросов на один слот гарантированно создают ровно одну запись (код 201), а остальные 19 получают 409 Conflict.
- **Тест на повторную доставку сообщений (at-least-once)**: повторное получение одного и того же event_id пропускается воркером без отправки дубликата клиенту.

## Архитектурные решения

### 1. Выбор брокера: RabbitMQ
Выбран **RabbitMQ** вместо Kafka по следующим причинам:
- Из коробки поддерживается механизм Dead Letter Exchange (DLX) и реализация Dead Letter Queue (DLQ).
- RabbitMQ легче в развертывании и эксплуатации для заданного объема микросервисов.

### 2. Transactional Outbox
- При создании или отмене бронирования запись в таблицы `bookings` и `outbox_events` происходит в единой транзакции PostgreSQL.
- Если брокер RabbitMQ временно недоступен, клиент всё равно получает успешный ответ, а событие сохраняется в БД со статусом `PENDING`.
- Фоновый процесс (OutboxService) вычитывает неотправленные события пачками с блокировкой, отправляет в RabbitMQ и переводит в статус `PROCESSED`.

### 3. Защита от двойного бронирования слота на уровне БД
- Защита реализована через частичный уникальный индекс в PostgreSQL:
  ```sql
  CREATE UNIQUE INDEX uq_booking_master_active_slot 
  ON bookings (master_id, start_at) 
  WHERE status = 'CONFIRMED';
  ```
- Даже при одновременном прохождении валидации в коде на уровне БД второй `INSERT` падает с ошибкой `UniqueViolation`, перехватывается сервисом и отдаёт клиенту HTTP 409 Conflict. При отмене брони (`status = 'CANCELLED'`) слот автоматически освобождается для повторной записи.

### 4. Идемпотентность API
- Эндпоинт `POST /bookings` требует заголовок `Idempotency-Key`.
- Результат успешного выполнения кэшируется в таблице `idempotency_keys`. Повторный запрос с тем же ключом не создаёт новую запись в БД, а возвращает сохранённый ответ.

### 5. Напоминания за 24 часа до визита
- Реализован планировщик (ReminderService)
  - Выбирает подтверждённые бронирования с условием времени `start_at <= NOW() + 24h` и флага `reminder_sent = false`.
  - Выставляет флаг `reminder_sent = true` и генерирует событие `booking.reminder` в outbox.

### 6. Кэширование и Rate Limiting в Redis
- Свободные слоты мастера кэшируются по ключу `slots:{master_id}:{date}`. При создании или отмене записи кэш инвалидируется.
- Лимит не более 3 уведомлений в час на одного клиента контролируется счётчиком в Redis (`INCR` + `EXPIRE`).

### 7. Сквозное логирование
- Все логи пишутся в JSON-формате через `structlog`.
- Сквозной `X-Correlation-ID` генерируется на уровне HTTP middleware, пробрасывается в заголовки сообщений RabbitMQ и связывает логи API и воркера.
